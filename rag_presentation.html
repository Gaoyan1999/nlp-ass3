Stage 01 · Data
batuhanmtl / job-skill-set
§ 03 · Stage 01 · Load

From raw rows to
JobPosting objects.

We load batuhanmtl/job-skill-set from HuggingFace — 1,167 postings across five categories: HR, IT, Business Development, Finance and Sales.

Each row is cleaned into a typed JobPosting dataclass and the full collection is dumped to data/job_postings.json — the single source of truth for the offline indexing job.

Implemented in data/load_dataset.py. The JSON file is git-ignored. 

# JobPosting schema
job_id          str
category        str      # 1 of 5
job_title       str
job_description str
job_skill_set   list[str]
Cleaned, typed, persisted to disk04 / 09
Stages 02-03 · Embed + Index
OpenAI · Pinecone
§ 04 · Stages 02-03

One vector per job.
Stored in Pinecone.

Per job we concatenate job_title + job_description + job_skill_set into one embedding text — title gives the role signal, description gives semantics, skills give the explicit requirements.

We embed with text-embedding-3-small → 1,536-dim dense vectors and upsert each into Pinecone alongside its metadata. job_id and category stay as metadata only — they aren't part of the embedded text. 

# Pinecone index
index     job-skill-rag
namespace job-skill-set
type      dense
dimension 1536
metric    cosine
records   1167

Stage 04 · Retrieve
The "R" in RAG
§ 05 · Stage 04

Resume in.
Top-K jobs out.

The resume — pasted text or text extracted from an uploaded PDF — is embedded with the same model used for jobs, so the two vectors live in the same space.

Pinecone returns the top k matches by cosine similarity. We map each raw match into a clean RetrievedJob object so the rest of the app never sees Pinecone-shaped JSON.

Optional category filter is forwarded as a Pinecone metadata filter — narrows the search server-side. 

# Per-resume query
index.query(
  vector=resume_vector,
  top_k=10,
  include_metadata=True,
  namespace="job-skill-set",
  filter=category_filter,
)
Same model both sides → same vector space06 / 09
Stage 05 · Score
Deterministic · auditable
§ 06 · Stage 05

A score the user can read.

match_score =
0.5 · semantic_pct  +  0.3 · skill_overlap_pct  +  0.2 · category_bonus
50%
Semantic
Cosine rescaled so 0.25 → 0% and 0.85 → 100% — embeddings rarely reach 1.0.
30%
Skill overlap
Normalised string match between resume skills and JD skills. Drives the missing-skills list.
20%
Category bonus
100 if predicted resume category matches JD category, else 0 — ties this feature back to the classifier.
Computed in Python · no LLM in the loop here07 / 09
Stage 06 · Explain
gpt-4o-mini · grounded JSON
§ 07 · Stage 06

The LLM explains.
It doesn't score.

gpt-4o-mini receives the resume, retrieved jobs, backend match scores, matched / missing skills and JD excerpts. The system prompt forbids fabricated numbers — scores are already final.

Output is strict JSON: ranked_matches, skill_gaps, notes. On malformed output a deterministic fallback fires so the API never returns an unusable response. 

"ranked_matches": [
  {

    "missing_skills": ["Power BI"]

],
"skill_gaps": [

Why this is RAG
§ 08 · Recap

Retrieval · Augmentation · Generation.

R
Retrieval
Pinecone returns the most semantically similar job postings to the resume vector.
A
Augmentation
Retrieved jobs and our deterministic match scores are inserted into the LLM prompt as evidence.
G
Generation
gpt-4o-mini generates skill-gap explanations grounded in retrieved jobs — never from memory.
