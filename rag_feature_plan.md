# Plan: Resume → Job RAG Matcher (Second Feature)

## Context

**Assignment**: UTS NLP Assessment 3 — group project, due 2026-05-15. Report (~3500 words, 40 marks) + 4-min presentation (10 marks). Need a real-world NLP problem with creative, well-justified solution.

**Dataset**: `batuhanmtl/job-skill-set` (HuggingFace) — 1,167 job postings. Fields: `job_id`, `category` (HR / IT / Business-Dev / Finance / Sales), `job_title`, `job_description`, `job_skill_set` (list of extracted skills).

**Already built**: 5-way category classifier on `job_description`.

**This plan**: Add a second feature using **vector DB + RAG** to lift the project into the rubric's "Excellent" tier.

**Vector DB decision**: We will use **Pinecone (online managed service)** as the sole vector store. No local FAISS fallback. The repo will document the required `PINECONE_API_KEY` and `OPENAI_API_KEY` in `.env.example`, and the report will note that retrieval calls a hosted serverless index (AWS, us-east-1).

---

## What We're Building

A **Resume → Job RAG Matcher** with two outputs:

1. **Top-K matching jobs** for a pasted resume (semantic retrieval).
2. **Skill-gap explanation** generated by an LLM grounded in the retrieved jobs ("you're missing X, Y to be competitive for these roles").

The existing category classifier becomes a **filter / re-rank signal** (e.g. user can constrain to Finance jobs, or boost in-category matches), giving a single coherent narrative across both features.

## Pipeline

### Indexing (one-time, offline)

1. Load 1,167 rows from HuggingFace.
2. For each row, build an embedding text = `f"{job_title}\n{job_description}\nSkills: {job_skill_set}"`.
3. Embed with `text-embedding-3-small`.
4. Upsert into Pinecone with metadata: `{job_id, category, job_title, skills}`.

### Query (online)

1. User pastes resume → optional category filter from existing classifier.
2. Embed resume with same model.
3. Pinecone `query(top_k=10, filter={category: ...})`.
4. **Compute hybrid match score** (see "Match Score Formula" below) per retrieved JD.
5. Build RAG prompt:
   - System: "You are a career coach. Given a resume and candidate jobs, return JSON with `ranked_matches` (with `why_match` citing JD phrases) and `skill_gaps` (skills the resume lacks across these jobs). Do NOT fabricate a numeric score — the backend computes it."
   - User: resume + top-K jobs (title + skills + truncated description) + pre-computed match scores.
6. Call `gpt-4o-mini` with `response_format=json_object`.
7. Frontend renders ranked matches with match-score breakdown + consolidated skill-gap list.

## Match Score Formula (user-facing percentage)

A single 0–100 percentage shown next to each retrieved JD in the UI and used for ranking. **Computed deterministically in Python**, not by the LLM, so it is reproducible and defensible in the report.

### Formula

```python
match_score = round(
    0.5 * semantic_pct        # rescaled cosine similarity
  + 0.3 * skill_overlap_pct   # lexical skill set overlap
  + 0.2 * category_bonus      # classifier agreement bonus
, 1)
```

### Component definitions

1. **`semantic_pct`** — anchor-rescaled cosine similarity, clamped to [0, 100]:
   ```python
   FLOOR, CEILING = 0.25, 0.85   # calibrated on the dataset (see below)
   semantic_pct = max(0, min(1, (cosine_sim - FLOOR) / (CEILING - FLOOR))) * 100
   ```
   - **Why rescale**: raw cosine for OpenAI embeddings rarely exceeds ~0.85 even for near-identical text. Showing raw 0.62 as "62%" misleads users.
   - **Calibration**: pick `FLOOR` = mean cosine of ~500 random cross-category JD pairs (≈0.2–0.3); pick `CEILING` = 0.85 (top of empirical range) or 1.0 if you'd rather have a hard ceiling.

2. **`skill_overlap_pct`** — fraction of the JD's required skills that appear in the resume:
   ```python
   skill_overlap_pct = len(resume_skills & jd_skills) / len(jd_skills) * 100
   ```
   - Skills are lowercased + stripped before set intersection.
   - This is the **mechanical, verifiable** signal — easy to defend in the report.

3. **`category_bonus`** — uses the existing classifier from feature 1:
   ```python
   category_bonus = 100 if predicted_resume_category == jd_category else 0
   ```
   - Run the trained classifier on the resume; bonus fires when it agrees with the JD's category.
   - This is the explicit **bridge between feature 1 (classification) and feature 2 (RAG)** — strengthens the project's "single coherent narrative" framing.

### Report justification (paragraph to write up)

> "We define `match_score` as a weighted sum of three signals: anchor-rescaled cosine similarity (50%), lexical skill-set overlap (30%), and classifier-predicted category agreement (20%). The semantic component captures paraphrased requirements that lexical methods miss; the skill component grounds the score in concrete, verifiable matches the user can audit; the category component reuses our trained classifier as a coarse-grained correctness check. Weights were chosen to prioritise semantic understanding while preventing high scores from purely numeric similarity in the absence of skill overlap. The score is **not** a probability of being hired — it is the system's confidence that the JD's requirements align with the resume."

### Implementation notes

- Compute `FLOOR` once during indexing — sample 500 random pairs, take mean cosine, store as a constant.
- Skills must be normalised consistently between resume and JD (lowercase, strip punctuation, remove duplicates) **before** set operations.
- Component sub-scores must also be returned to the frontend so the breakdown is visible — not just the aggregate.

## Real-World Problem & Impact (for report Introduction)

- **Problem**: ATS keyword matching rejects qualified candidates because phrasing doesn't match (e.g. "stakeholder management" vs "client relations"). Job seekers waste hours filtering postings.
- **Impact**: Better semantic matching reduces false rejections; skill-gap output gives actionable upskilling advice — directly translatable to career outcomes.

## Technical Challenges (for report Background — need ≥3 for full marks)

1. **Semantic vs lexical matching** — why TF-IDF/BM25 misses paraphrases; how dense embeddings handle it; cosine geometry of embedding space.
2. **Skill-set noise & canonicalisation** — "Python" vs "python programming" vs "Py"; trade-offs of normalising before embedding vs trusting the model.
3. **Hallucination control in RAG** — strategies: structured JSON output, grounding instructions, citing retrieved `job_id`s in `why_match`.
4. *(Optional 4th)* **Evaluation without ground-truth resume↔job pairs** — held-out self-retrieval, ablation against TF-IDF baseline.
